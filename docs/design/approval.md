# 审批交互设计

状态：目标设计与当前边界。当前持久化等待、批准消费和显式续跑见[等待与续跑](../runtime/agent-runtime.md#等待与续跑)，已实现资格和有效性见[运行控制参考](../reference/runtime-control.md)；本页保留跨界面、跨设备授权目标，不新增审批消息字段或签名协议。

## 目标

让 CLI、TUI、桌面应用、远程界面与子代理使用同一授权语义。Runtime 产生待决定动作，界面呈现具体范围并转交人的决定，Runtime 校验后执行。

Policy 可直接允许的动作无需人为确认；需要人的授权不能由模型或代理自行替代。传递审批是转交交互，不是新的授权主体获得无限批准能力。

## 必须明确的语义

请求需关联主体、任务、实际动作、资源、目标与约束。决定只能适用于该范围；修改动作、资源、工作空间或恢复条件时需核对仍否有效。

需要区分拒绝、尚未回复、取消、过期和运行失败，不能把没有答案当成允许。任务取消后迟到批准不能启动旧动作；撤销和恢复不能隐式复用无效决定。

## 交互与后台运行

不同界面可以用不同 UI，但共享请求状态与验证。无交互后台遇到未获许可动作时保留阻塞与证据，而不是自动提权或反复调用模型猜测权限。

子代理可向父任务提交额外权限需求，由父任务在已有用户范围内处理；跨设备决定依赖共享信任事实。不能从公共摘要读取一句“已批准”作为可执行许可。

## 设计与验收顺序

先定义状态关联、有效性、并发和取消，再协商消息契约和传输。验收覆盖重复决定、迟到回复、篡改动作、重连、任务续跑和授权撤销。当前持久化审批绑定具体动作指纹，批准按现行控制参考校验和消费；同步回调仅在执行槽外收集决定，不构成同一 Run 内可反复使用的许可。路径访问批准授予明确路径范围，续跑不能因路径目标变化扩大该范围。未来若提供更宽的批准范围，应由人明确选择并作为可校验的授权范围保存，不能由工具名和风险级别推断。
